## Finding Details

### FINDING-001 — HIGH — Timer sync violation (NHIE + Exposed) — FIXED

**Files:**
- `src/games/never-have-i-ever-18/NeverHaveIEverEngine.tsx:266`
- `src/games/exposed/ExposedEngine.tsx:321`

**Problem:**
Both NHIE and Exposed game clients computed the display timer as:
```ts
timeLeft={Math.max(0, VOTE_SECONDS - Math.floor((Date.now() - remote.startTime) / 1000))}
```
This violates the CLAUDE.md timer sync rule: host and client clocks can drift by several seconds, causing clients to show incorrect timers and potentially submit answers after the host has already scored the round.

MLT correctly uses `remote.timeLeft` (authoritative broadcast value). NHIE and Exposed were missing `timeLeft` from their broadcast event types entirely.

**Fix applied:**
1. Added `timeLeft: number` to `NHIEStateEvent` and `ExposedStateEvent` in `src/shared/types/broadcast.ts`
2. Updated host `buildEvent()` in both engines to include `timeLeft: state.timeLeft`
3. Changed client render calls to use `remote.timeLeft` directly

**Commit:** `fix(review): FINDING-001 — timer sync violation in NHIE and Exposed engines`

### FINDING-003 — MEDIUM — Weak profile ownership check — Deferred

**File:** `pages/api/profile/[sessionId].ts:29`

**Problem:**
The PUT endpoint "ownership check" compares `callerSessionId` (from request body) to `sessionId` (from URL param). An attacker who knows a victim's `sessionId` (a UUID opaque identifier) can set both fields to the same value and overwrite the victim's display name. Since `sessionId` is never publicly exposed in the UI, the practical risk is low. However, the check provides no actual cryptographic proof of ownership.

**Why deferred:**
The session model is "UUID as bearer token" — knowledge of the UUID is the authorization. This is a pre-existing design pattern used across the entire app. Fixing it properly would require signed tokens or server-side session management (out of scope for this branch). The display name mutation's blast radius is minimal (cosmetic only, not financial or PII).

**Recommended future fix:** Add `updated_at` rate-limiting per sessionId or use Supabase RLS instead of service-role writes.

### FINDING-004 — MEDIUM — Exposed `submittedCount` hardcoded to 0 — Deferred

**File:** `src/games/exposed/ExposedEngine.tsx` (client render block ~line 319)

**Problem:**
```ts
submittedCount={0} // clients don't track this count
```
The `ExposedView` shows "X of N players submitted" using `submittedCount`. Clients see 0/N even when other players have submitted. The host broadcasts `ExposedStateEvent` which does not include submission count (submissions are kept anonymous until reveal).

**Impact:** Clients get no feedback during the submission window about how many peers have submitted, creating uncertainty about whether the game is progressing.

**Recommended fix:** Add `submittedCount: number` to `ExposedStateEvent` (just the count, not the contents or identities). Host broadcasts `state.submissionsRaw.length` — safe since counts don't reveal who submitted what.

### FINDING-005 — MEDIUM — JSONB containment query may be unreliable — Deferred

**File:** `pages/api/stats/[sessionId].ts:30-38`

**Problem:**
```ts
.contains("results", { players: [{ profile_id: sessionId }] })
```
Supabase's `@>` JSONB containment operator checks if the left value contains the right value. For arrays, this checks whether every element on the right appears in the left array. The `results.players` field is a JSONB array of player objects. The query checks if any element matching `{ profile_id: sessionId }` exists, but Postgres's `@>` for arrays checks that the entire element matches (all other keys must match too, or the element must be exactly that object). In practice, a player object has multiple fields (`id`, `name`, `score`, etc.) so `[{ profile_id: sessionId }]` would NOT match player objects that have more fields.

**Why deferred:** This is pre-existing behavior and the tests pass because they mock Supabase. Real-world behavior would depend on the Postgres version's JSONB handling. Fixing it requires a raw SQL filter or a Postgres function — out of scope for this review.

**Recommended fix:** Use a Postgres RPC or raw SQL: `WHERE results->'players' @> jsonb_build_array(jsonb_build_object('profile_id', $1::text))`.
